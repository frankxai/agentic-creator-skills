# /build-search-authority

> Use this command before `/create-content` when the work targets durable search demand, a long-tail category, a pillar page, or several related pages.

## Operating Principle

A keyword is not a commission. The command must prove that a page deserves to exist, assign a canonical owner, specify an original artifact, and define how the page creates value before drafting begins.

## Workflow

### Step 1: Resolve the Task Envelope

Extract or establish:

- category or problem territory
- canonical brand and domain
- audience and job-to-be-done
- commercial or capability outcome
- existing URLs, products, evidence, and media
- available demand sources and publication constraints

When information is missing, use repository, analytics, connected knowledge-base, and product evidence first. Ask one focused question only when the missing decision cannot be resolved from available context.

### Step 2: Load the Search Authority Skill

Apply `search-authority` in full.

Do not load the writing skill yet.

### Step 3: Audit Before Ideation

Inspect the current estate for:

- overlapping pages and titles
- existing authority, traffic, conversions, and internal links
- products, assessments, tools, frameworks, code, media, and case evidence
- content that should be refreshed, merged, redirected, or retired
- category ownership conflicts across brands

Return a concise estate decision table.

### Step 4: Build the Opportunity Graph

Create:

1. category thesis
2. canonical ownership map
3. intent–entity–job–URL graph
4. query hypotheses grouped by reader decision rather than wording
5. collision and cannibalization map
6. product and offer bridges

Prioritize first-party evidence. Mark all estimates and weak signals explicitly.

### Step 5: Run the Commission Gate

Score every proposed page using the 16-point commission rubric.

For each proposal return exactly one decision:

- `PASS` — commission the page
- `MERGE` — add to an existing canonical page
- `HOLD` — gather evidence or build the artifact first
- `KILL` — no strategic reason to create it

No more than three pages may pass in the first wave.

### Step 6: Design the Proof Wave

The default proof wave contains:

- one category authority page
- one decision or implementation asset
- one proof asset

For every approved asset specify:

- proposed URL and internal-link role
- target job and exclusion boundary
- differentiated thesis
- evidence ledger
- original artifact
- primary action and product bridge
- distribution derivatives
- author, reviewers, maintainer, and measurement dates

### Step 7: Produce Execution-Ready Packets

Create one page commission packet per approved asset. The packet must be sufficient for another agent to research, write, implement, review, and ship without reinterpreting the strategy.

When a connected work-management system exists, create or update:

- one campaign or project record
- one content item per approved page
- production tasks for research, artifact creation, drafting, review, implementation, QA, distribution, and measurement

Do not create a new dashboard when a canonical content system already exists.

### Step 8: Route Production

For each approved packet:

1. research and claim ledger
2. original artifact or direct media
3. outline and answer-unit architecture
4. `/create-content`
5. `/content-review`
6. repository branch and pull request
7. rendered preview, mobile QA, metadata/schema/canonical checks
8. operator-approved publication
9. distribution
10. T+7, T+28, and T+90 learning reviews

Return:

```text
The single decision unlocked by the first evidence window.
```

## Hard Constraints

- No keyword stuffing or page-per-variant plans
- No fabricated traffic, volume, conversion, experience, or benchmark claims
- No generic CTA disconnected from reader intent
- No publication without original value and a maintenance owner
- No direct production release without independent review and rendered-preview evidence
- No cluster expansion before the proof wave has completed its learning window
